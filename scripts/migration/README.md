## Навіщо

Хмарний проєкт `${PROJECT_REF}` (`supabase-accounts`, eu-west-2, PG 15.8) **перевищив квоту трафіку**
на безкоштовному тарифі і зараз обмежений:

```
REST /rest/v1      → 402  "exceed_egress_quota"
Storage /storage/v1 → 402
Auth /auth/v1      → 402
Management API     → працює (через нього й мігруємо)
```

Місце в базі ні до чого: 49 МБ із 500 МБ. Точну причину з боку коду не видно —
див. розділ про картинки нижче, версія «винен фавікон» виявилась хибною.

## Куди

Self-hosted Supabase на VPS, PostgreSQL 15.8 — той самий мажор, що й джерело.
База була порожня, потрібні розширення (`pgcrypto`, `uuid-ossp`) на місці.

Адреса — у `VPS_SUPABASE_URL`, ключ — у `SERVICE_LOCAL_KEY`, обидва в `.env`
(він у `.gitignore`; репозиторій публічний, тому в самих скриптах хостів немає).
Обгортка для SQL — [`pg.mjs`](pg.mjs):

```bash
node --env-file=.env scripts/migration/pg.mjs -e "select 1"
```

Маршрут `/mcp` на цьому VPS віддає `403` із будь-яким заголовком — MCP там не працює, не витрачайте час.

## Порядок

| Крок | Файл | Що робить |
| :-- | :-- | :-- |
| 1 | `1-dump.sh` | дамп схеми + даних із проду (потрібен Docker) |
| 2 | `6-restore-http.mjs` | заливка в VPS через `/pg/query` |
| 3 | `4-storage-files.mjs` | 128 файлів Storage |
| 4 | `5-rewrite-urls.sql` | 110 посилань на картинки з проду → на VPS |
| 5 | `3-verify.sql` | звірка кількості рядків із продом |

`2-restore.sh` і `probe-auth.sh` — запасні, для варіанту через psql. Основний шлях — HTTP.

### Якщо Docker недоступний

Крок 1 замінюється на MCP хмарного проєкту (`.mcp.json` → `mcp.supabase.com`, `project_ref=${PROJECT_REF}`):

- **схема** — зібрати DDL із каталогу: `pg_get_constraintdef`, `pg_get_indexdef`,
  `pg_get_triggerdef`, `pg_get_functiondef`, `pg_policies`, `pg_sequences`;
- **дані** — вичитати `SELECT`-ами, вставити в VPS через `/pg/query`;
- **перевірка** — звірити каталоги обох баз: таблиці, колонки, констрейнти,
  індекси, політики RLS, функції. Збігається — схема відтворена точно.

PostgREST проду для цього **не годиться** — він віддає 402.

## Картинки

| Де | Скільки |
| :-- | :-- |
| У R2 (`dns.devicehelp.cz`) | 257: моделі 243, серії 8, статті 6 |
| Мертві посилання на прод | 34: моделі 20, послуги 11, бренди 3 |

**Файли з проду не завантажити — Storage віддає 402.**

74 картинки моделей відновлено з кешу оптимізатора Next скриптом
[`recover-images.mjs`](recover-images.mjs) (`scan` — подивитись, `recover` — залити в R2
й оновити базу). Ключ теки кешу це `base64url(sha256(4 + href + width + quality + mimeType))`,
тому кеш зіставляється з URL перебором.

Важливо: **це не оригінали** — 256 px AVIF по ~4 КБ замість ~26 КБ. У кеші є тільки
ширини 128 і 256, бо більшими сайт їх ніде не показує; для поточної верстки цього досить.
Картинки послуг, брендів, серій і статей через оптимізатор не проходили — у кеші їх немає.

**Повне відновлення — після скидання квоти** (цикл від дати проєкту, 20 квітня → ~20 числа).
Тоді Storage проду знову відкриється, і треба забрати всі 108 оригіналів у R2
скриптом [`4-storage-files.mjs`](4-storage-files.mjs), переписавши в ньому призначення на R2.
Оригінальні URL не втрачені — вони й далі лежать у базі **проду**, яка читається напряму.

**Фавікон і лого вже не проблема.** У базі лежав PNG на 876 КБ, але він **ніколи не віддавався**:
у `normalizeSiteAssetPath` ([lib/site-assets.ts](../../lib/site-assets.ts)) є список legacy-маркерів,
і цей файл там — код підміняє його на `public/devicehelp-favicon-32.png` (1.5 КБ). У HTML живого
сайту стоїть саме статика. На VPS значення `app_settings.site_favicon` / `site_logo` вже переписані
на статичні шляхи, щоб не тягнути мертве посилання.

Тобто версія «квоту вибрав фавікон» — **хибна**. Чим саме вибрало, з боку коду не видно:
кандидати — картинки послуг (11 × ~142 КБ) і моделей (94 × ~26 КБ) із Supabase Storage
плюс читання даних через REST. Розкладку по джерелах показує лише дашборд Supabase.

## Причина, чому половина картинок застрягла — виправлено

Раніше в `app/api/admin/upload/route.ts` гілка на R2 ловила тільки `article | model | series`,
а `service`, `logo` і `favicon` провалювались у стару гілку Supabase Storage. Тому моделі
поступово доїжджали в R2 при перезаливці, а послуги й лого не переїхали б ніколи.

Роут переписано: **усі завантаження йдуть у R2**, Supabase Storage більше не задіяний.
Теки за типом (`models`, `services`, `brands`, `logo`, `favicon`, `articles`, `series`),
імена завжди унікальні — нічого не перезаписується, тому віддається з
`max-age=31536000, immutable`. SVG та ICO заливаються без обробки: `sharp` або
растеризував би SVG, або зовсім не прийняв ICO. Растр і далі стискається у WebP.

Лого брендів раніше йшли без типу і потрапляли в теку `models/`; тепер сторінка брендів
передає `type=brand`.

`lib/image-processor.ts` → `validateImageFile` після цієї правки більше ніде не викликається
(перевірка типів і розміру тепер у самому роуті) — можна прибрати при нагоді.

## Після переїзду

Створити `.env.local` (Next.js дає йому пріоритет над `.env`, відкат — просто видалити файл):

```
NEXT_PUBLIC_SUPABASE_URL=${VPS_SUPABASE_URL}
SUPABASE_URL=${VPS_SUPABASE_URL}
SUPABASE_SERVICE_ROLE_KEY=<SERVICE_LOCAL_KEY>
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon вашої інсталяції>
SUPABASE_ANON_KEY=<anon вашої інсталяції>
POSTGRES_URL=postgresql://postgres:<пароль>@<хост>:5432/postgres
```

`SUPABASE_JWT_SECRET` **не потрібен** — у коді він ніде не читається (єдина згадка це
прокидання змінної в `docker-compose.yml`). Supabase Auth не використовується.

Supabase Auth не використовується — `auth.users` порожня, у застосунку власні `users`/`sessions`
у схемі `public`. Мігрувати там нічого.
